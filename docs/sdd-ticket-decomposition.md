## 1. Принцип декомпозиції

Декомпозиція сформована для невеликої команди без поточного плану розширення. Тікети не деталізуються до рівня кожної окремої вимоги; вимоги групуються у мінімальні основні GitHub Issues за SDD-циклом і головними функціональними блоками системи.

Кожна вимога з SRS має стабільний ID формату `REQ-F-*` або `REQ-NF-*`. Ці ID вказуються в body кожного issue в полі `Requirement IDs`, щоб надалі підтримувати трасування між SRS, тестами, реалізацією, перевіркою і документацією.

---

## 2. Подання типів SDD у GitHub Issues

У GitHub Issues тип тікета задається label. Для поточного проєкту достатньо одного основного type-label на issue.

| Тип SDD | GitHub label | Функціональне призначення |
|---|---|---|
| Specification | `type: specification` | Базова специфікація, межі системи, глосарій, правила ID вимог. |
| Addendum | `type: addendum` | Контрольовані уточнення, out-of-scope рішення, відкладені вимоги. |
| Test | `type: test` | TDD/BDD тести до реалізації функціоналу. |
| Feature | `type: feature` | Реалізація основних можливостей системи. |
| Verification | `type: verification` | Перевірка відповідності реалізації ID вимог і матриці трасування. |
| Validation | `type: validation` | Приймальна перевірка критеріїв прийняття та BDD-сценаріїв. |
| Documentation | `type: documentation` | Супровідна документація проєкту. |
| Gate | `type: gate` | Контрольна точка готовності артефактів SDD-циклу. |

Додаткові labels без створення нових типів тікетів: `area: auth`, `area: activity`, `area: history`, `area: docs`, `area: gate`, `status: planned`.

## 5. Мінімальний шаблон GitHub Issue

```markdown
## Type
type: <specification | addendum | test | feature | verification | validation | documentation | gate>

## Requirement IDs
- REQ-...

## Scope
Короткий опис основної роботи в межах issue.

## Done When
- Пов'язані вимоги покрито або перевірено.
- Результат можна трасувати до `spec/srs.md`.
```

## 6. Правило подальшого ведення

Для поточного розміру команди ці GitHub Issues є основними одиницями планування. Додаткове дроблення дозволене лише якщо окремий issue стає неможливо виконати або перевірити як одну завершену одиницю роботи.

---

## 7. Розподіл відповідальності

Валідація задуму та рішення Gate не делегуються агенту. Агент може підготувати матеріали, перевірки й чернетки, але фінальне прийняття цих рішень залишається за людиною.

| Тип роботи | Переважний виконавець | Пояснення |
|---|---|---|
| Specification | Агент | Агент готує структуру, формулювання, ID вимог і трасування; людина переглядає зміст. |
| Addendum | Спільно | Агент оформлює уточнення, людина підтверджує зміну обсягу або відкладення. |
| Test | Агент | Агент готує TDD/BDD тести за SRS і критеріями прийняття. |
| Feature | Агент | Агент реалізує функціонал за затвердженими issue та вимогами. |
| Verification | Агент | Агент перевіряє відповідність коду, тестів і документації ID вимог. |
| Validation | Людина | Людина підтверджує, що задум і приймальна поведінка відповідають очікуванню; агент лише готує сценарії та звіт. |
| Documentation | Агент | Агент оновлює супровідні документи, матрицю трасування та інструкції. |
| Gate | Людина | Людина ухвалює Gate-рішення; агент готує підсумок, ризики й докази готовності. |

## 8. Поетапний план

| Етап | Орієнтовна тривалість | Залежності | GitHub Issues | Результат |
|---|---:|---|---|---|
| 1. Базова фіксація SRS і трасування | 0.5 дня | Затверджена SRS | `SDD-SPEC-001`, `SDD-DOC-001` | SRS, реєстр ID вимог і матриця простежуваності узгоджені. |
| 2. Уточнення обсягу | 0.5 дня | Етап 1 | `SDD-ADD-001` | Out-of-scope та відкладені вимоги зафіксовані без розширення обсягу. |
| 3. Базове тестове покриття | 1 день | Етапи 1-2 | `SDD-TEST-001` | Підготовлені основні TDD/BDD тести для вимог, що реалізуються. |
| 4. Авторизація та доступ | 1-1.5 дня | Етап 3 | `SDD-FEAT-AUTH-001` | Реєстрація, вхід, обмеження доступу й базова ізоляція користувача. |
| 5. Створення записів активності | 1-1.5 дня | Етапи 3-4 | `SDD-FEAT-ACTIVITY-001` | Додавання Activity Entry, довідник вправ, валідація дати, тривалості й нотаток. |
| 6. Історія, фільтри й підсумки | 1-1.5 дня | Етапи 4-5 | `SDD-FEAT-HISTORY-001` | Перегляд власних записів, фільтрація, пошук, підсумки й порядок відображення. |
| 7. Редагування та видалення | 1 день | Етапи 4-6 | `SDD-FEAT-MAINTAIN-001` | Редагування й остаточне видалення власних записів із забороною доступу до чужих. |
| 8. Verification | 0.5 дня | Етапи 3-7 | `SDD-VER-001` | Перевірено трасування вимог до тестів, реалізації та документації. |
| 9. Validation | 0.5 дня | Етап 8 | `SDD-VAL-001` | Людина підтверджує відповідність задуму та приймальним сценаріям. |
| 10. Gate | 0.25 дня | Етапи 8-9 | `SDD-GATE-001` | Людина ухвалює рішення Gate на основі підготовлених доказів. |

Загальна оцінка для малої команди: приблизно 7-9 робочих днів без розширення обсягу. Окрема оцінка людських дій, ризики та Gate-перевірки для вимог з вищою ціною відмови зафіксовані в `docs/sdd-risk-and-human-plan.md`.
